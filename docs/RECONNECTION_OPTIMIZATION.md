# VPN 断线重连优化说明

## 问题描述
原有实现在断开连接后重新连接时加载时间过长，用户体验不佳。

## 优化措施

### 1. **加速网络切换响应** （100ms vs 500ms）
- **位置**: `Command.Available` 和 `Command.Lost` 处理
- **优化**: 网络恢复或切换时的延迟从 500ms 降至 100ms
- **效果**: 网络切换后立即重连，减少 400ms 等待

### 2. **优化重试退避策略** （总计 6.7s vs 15s）
- **原策略**: 1s → 2s → 4s → 4s → 4s（总计 15 秒）
- **新策略**: 200ms → 500ms → 1s → 2s → 3s（总计 6.7 秒）
- **原理**: 早期失败往往是瞬时问题（网络切换、DNS 波动），快速重试可大幅降低感知延迟
- **效果**: 首次重试几乎立即进行，总重试时间减少 55%

### 3. **加速配置变更重连** （150ms vs 400ms）
- **位置**: 设置或节点变更的 debounce 时间
- **优化**: 从 400ms 降至 150ms
- **效果**: 切换节点或修改设置后快速生效

### 4. **智能核心复用机制** （节省 200-500ms）
- **原实现**: 每次重连都完全停止并重启 xray-core 和 tun2proxy
- **新机制**:
  - 同节点重连：保留 xray-core 进程，只重启 tun2proxy
  - 检测 xray-core 运行状态，避免重复启动
  - 异常情况（核心崩溃）时仍完全清理
- **效果**: 同节点重连时节省 xray 启动时间（约 200-500ms）

### 5. **保留 TUN 设备状态**
- **原实现**: 重连时关闭 TUN 设备
- **新机制**: 快速重连时保持 TUN 设备打开，仅重启隧道
- **效果**: 减少系统调用开销，加快隧道重建速度

## 代码变更位置

### IceFlowVpnService.kt

1. **onCreate**: 配置变更 debounce 400ms → 150ms
2. **scheduleRetry**: 重试策略优化，200/500/1000/2000/3000ms
3. **cleanup**: 新增 `stopXray` 参数，支持选择性清理
4. **Command.Switch**: 同节点时复用 xray-core
5. **Command.Retry**: 自动重试时智能判断是否复用
6. **Command.RetryNow**: 手动重试时智能判断
7. **Command.CoreFailed**: 崩溃时强制完全清理
8. **Command.Available/Lost**: 网络事件时智能复用 + 快速重连
9. **startVpn**: 检测 xray 运行状态，避免重复启动

## 性能提升预估

**典型重连场景（同节点，网络短暂中断）**:
- **原耗时**: 500ms (网络延迟) + 1000ms (第一次重试) + 300ms (启动) ≈ 1.8 秒
- **新耗时**: 100ms (网络延迟) + 200ms (第一次重试) + 100ms (复用) ≈ 400ms
- **提升**: **约 78% 的时间节省**

**多次失败场景（网络不稳定）**:
- **原耗时**: 最多 15 秒才放弃
- **新耗时**: 最多 6.7 秒即反馈失败
- **提升**: **减少 55% 的无效等待**

## 测试建议

1. **正常重连**: 断开网络 → 恢复网络，观察重连速度
2. **节点切换**: 在连接状态下切换节点
3. **网络切换**: WiFi ↔ 移动网络切换
4. **异常恢复**: 模拟 xray-core 崩溃（kill 进程）
5. **长时间断网**: 断网 30 秒后恢复，验证快速恢复

## 兼容性说明

- 所有优化均向后兼容，不影响现有功能
- 核心崩溃时仍会完全清理，保证稳定性
- 失败场景下仍会回退到完全重启策略

## 注意事项

由于构建环境需要 Java 11+，请确保：
```bash
# 检查 Java 版本
java -version  # 应该是 11 或更高

# 如果使用 JAVA_HOME
echo $JAVA_HOME
```

## 日志监控

优化后的日志会显示：
- `[计时] xray.reuse (already running)` - 表示复用了现有 xray 进程
- 重连延迟会明显缩短（查看 `[计时]` 标记的时间戳）
